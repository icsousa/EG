1 · O problema

Os playbooks em YAML só revelam os erros durante um incidente real

Playbook numa plataforma SOAR (YAML): aceite sem nenhum aviso

- name: block
  action: block_ip
  input: "{{ alert.sorce_ip }}"        # ① campo mal escrito
- name: notify
  action: send_email
  body: "Chave: {{ secrets.api_key }}" # ② segredo por email
- name: isolate
  action: isolate_host                 # ③ sem condição

São 3 da manhã, um IP faz milhares de tentativas de SSH… e o bloqueio falha porque o campo não existe.

O mesmo playbook em Sentinela: rejeitado antes de ser ativado

E204 ① o alerta não tem o campo sorce_ip
E601 ② um segredo não pode ir para uma mensagem
W01 ③ ação destrutiva sem nenhuma condição

Os erros passam a ser apanhados às 3 da tarde, quando se escreve o playbook, e não às 3 da manhã, durante o ataque.

Contar a história: equipas de segurança (SOC) automatizam a resposta a ataques com playbooks, normalmente em YAML. O YAML não percebe nada do que está escrito: um campo mal escrito, uma chave enviada por email ou um bloqueio sem condição só se descobrem durante o incidente. A Sentinela deteta estes três problemas antes de o playbook ser ativado.
1 · A proposta

Uma DSL em que os conceitos de segurança e de rede são construções da linguagem

Utilizadores

Analistas de segurança (SOC) e engenheiros de redes e de operações.

Objetivo

Playbooks legíveis e verificáveis: um playbook com erros nunca chega a produção.

Domínio

Resposta automática a incidentes: port scan, brute force, flood, ARP spoofing.

ConceitoConstruçãoPara que serve
Alertaalert nome { campo: tipo; }esquema tipado dos dados que chegam do IDS
Playbookplaybook nome { … }conjunto de reações, com estado persistente
Handleron X as a { } · every 1h { }reage a cada alerta, ou à passagem do tempo
Tipos de redeip · cidr · durationnão se confunde um IP com uma rede: 10.0.0.0/8, 24h
Segredosecret token: string = …;credencial cujo fluxo é verificado
Explicar quem usa a linguagem e quais são os conceitos. A ideia central: os conceitos do domínio (alerta, IP, rede, duração, segredo) não são strings, são tipos e construções que a linguagem conhece e verifica.
1 · Modelo de execução

Um playbook é um serviço sempre ativo, verificado antes de ser ativado

playbook.sntescrito pelo analista
→
Gramática de atributossintaxe + semântica
→
✘ Erro → rejeitadoo playbook não é ativado
✔ Avisos → ativoos avisos ficam registados

on X as a

Corre sempre que chega um alerta do tipo X.

every 1h

Corre periodicamente, haja ou não alertas.

Estado persistente

As variáveis do playbook mantêm o valor entre execuções.

Estado local

As variáveis de um handler recomeçam em cada execução. Um handler de cada vez.

Diferença importante em relação a um script: o playbook fica sempre a correr. Cada alerta dispara o handler "on" desse alerta, e o "every" corre de X em X tempo. As variáveis do playbook são estado persistente (por exemplo, um contador de incidentes). Com um erro o playbook não é ativado; com avisos é ativado.
1 · A linguagem num exemplo

Brute force SSH: bloquear um IP externo com demasiadas tentativas

alert ssh_failed_login {
  src_ip: ip;
  user: string;
}

playbook brute_force_ssh {
  var limite: int = 5;
  var rede_interna: cidr = 10.0.0.0/8;

  on ssh_failed_login as a {
    var tentativas: int = count(a.src_ip, 10m);
    if (tentativas > limite and not (a.src_ip in rede_interna)) {
      block_ip(a.src_ip, 24h);
      notify("Brute force de " + str(a.src_ip));
    }
  }
}

Esquema do alerta

Os campos que chegam do IDS, com tipo. a.src_ip é verificado contra este esquema.

Tipos e literais de rede

10.0.0.0/8 é um cidr, 24h uma duration; ip in cidr é uma operação da linguagem.

Biblioteca de ações

block_ip, quarantine, rate_limit, log, notify · funções count, len, str.

Ler o exemplo em voz alta: "quando chega uma falha de login, conta as tentativas desse IP nos últimos 10 minutos; se forem mais de 5 e o IP não for interno, bloqueia 24 horas e avisa a equipa". Mostrar que se lê quase como português.

Quatro ataques reais, do mais fácil ao mais difícil

fácil

Port scan

fácil

intermédio

Limita cada origem fora da whitelist. for com if aninhado, contador.

difícil

Os quatro estão em exemplos/ e passam a verificação sem erros nem avisos. Cobrem as camadas de aplicação, transporte e ligação (L2).

O professor achava que 6 casos era demasiado; reduzimos para 4, com dificuldade crescente. Todos correspondem a ataques que se reproduzem com ferramentas reais. O difícil é o ARP spoofing, que está no slide seguinte.
1 · O caso difícil

ARP spoofing: segredo, estado persistente e every

playbook lan_integrity {
  secret webhook_token: string = "xoxb-123";
  var lan: cidr = 10.0.2.0/24;
  var servidores: list<ip> = [10.0.1.10, 10.0.1.20];
  var incidentes: int = 0;          # estado persistente

  on arp_spoof as x {
    var critico: bool = x.claimed_ip == x.gateway_ip;
    for srv in servidores {
      if (x.claimed_ip == srv) { critico = true; }
    }
    if (critico and x.attacker_ip in lan) {
      quarantine(x.attacker_ip);
      block_ip(x.attacker_ip, 1h);
      incidentes = incidentes + 1;
      notify("ARP spoofing por " + str(x.attacker_ip), webhook_token);
    } else {
      log("ARP suspeito: " + str(x.attacker_ip));
    }
  }

  every 1h {                       # haja ou não alertas
    if (incidentes > 0) {
      notify("Resumo: " + str(incidentes), webhook_token);
      incidentes = 0;
    }
  }
}

Segredo protegido

O webhook_token só pode ir para o 2.º argumento do notify (credencial). Num log seria o erro E601

Estado entre alertas

incidentes acumula de ataque em ataque e o every 1h envia o resumo e repõe o contador.

Ações destrutivas guardadas

quarantine e block_ip estão dentro de um if: fora dele seria o aviso W01

Este exemplo junta quase tudo: segredo, lista de IPs, variável bool alterada dentro de um for, várias ações e o handler every com estado persistente. É o que mostra que a linguagem não é trivial.

1 · Sintaxe

O texto é lido pelo parser LALR(1) gerado da GIC. Programa mal formado → erro de sintaxe com a linha.

2 · Semântica

O avaliador calcula os atributos numa travessia e verifica as condições de contexto. A primeira que falha para a avaliação.

3 · Resultado

Erro → playbook rejeitado. Sem erros → ativo, com os avisos do atributo warnings da raiz.

A grande decisão da v2.0: não há duas gramáticas. O sentinela.ag tem a gramática e a semântica no formato das aulas; o LarkAG gera o avaliador e nós geramos o parser LALR a partir da mesma gramática. O sentinela.py só junta as peças e mostra a linha do erro.

Prioridades

10.0.0.0/8 é um CIDR, não um IP seguido de outra coisa; 24h é uma DURATION, não INT + NAME.

Léxico vs semântica

O lexer aceita 300.1.1.1; é a semântica que o rejeita (E701).

Ponto principal: os literais de rede têm tokens próprios. Para não serem ambíguos entre si (um CIDR começa como um IP), usamos prioridades no lexer. E separamos o que é léxico (a forma) do que é semântico (a validade do valor).

Herdados ↓

vêm do pai ou dos irmãos à esquerda: o contexto (env, scope, alerttab, guarded, level, seen)

Sintetizados ↑

3 · Ler a semântica nas declarações

Só com as declarações dos atributos, já se leem as regras da linguagem

Padrão nas declaraçõesRegra da linguagem
env ↓ em todo o lado; envout ↑ nas sequênciasScopes estáticos e declarar antes de usar: o ambiente desce e cresce da esquerda para a direita
scope ↓, um por blocoNão se redeclara no mesmo bloco; um bloco interior pode reutilizar um nome
Env guarda a EspécieSegredos, variáveis do for e aliases têm regras próprias
type ↑ nas expressões, sem tipo herdadoTipagem de baixo para cima; os tipos das variáveis vêm de declarações explícitas
secret ↑ nas expressõesFluxo de informação: o que usa um segredo fica secreto
seen ↓ em alert, field, handlerCada alerta, campo e on é único
level ↓ em vardecl · guarded ↓ nas instruçõesA posição importa: segredos só no estado; ações destrutivas fora de if assinaladas
warnings é atributo; os erros são CCDois níveis: erros impedem a ativação, avisos não
Mensagem principal: a semântica lê-se nas declarações. Exemplos para dizer em voz alta: o env é herdado e cresce da esquerda para a direita, por isso as variáveis têm de ser declaradas antes de usadas. O type é sintetizado e não há tipo herdado, por isso o tipo de uma expressão vem só das suas partes. O secret é sintetizado, por isso qualquer expressão que use um segredo fica secreta.
3 · Gramática anotada

Cada produção tem regras de cálculo (ER) e condições (CC)

Notação matemática (GRAMATICA.md §4)

P21  vardecl → "var" NAME ":" datatype "=" expr ";"

ER
vardecl.envout = vardecl.env ⊕ {NAME ↦ (datatype.type, var)}
vardecl.scopeout = vardecl.scope ∪ {NAME}

CC
NAME ∉ vardecl.scope → E102
expr.type = datatype.type → E301
¬ expr.secret → E602

P47  primary → NAME

(primary.type, k) = primary.env(NAME) · primary.secret = (k = secret)

NAME ∈ dom(primary.env) → E101

A mesma produção em LarkAG (sentinela.ag)

vardecl : "var" NAME ":" datatype "=" expr ";"
ER {
  expr.env = vardecl.env;
  expr.alerttab = vardecl.alerttab;
  vardecl.envout = vardecl.env |
      { str(NAME) : (datatype.type, "var") };
  vardecl.scopeout = vardecl.scope | { str(NAME) };
  …
}
CC {
  str(NAME) not in vardecl.scope
      -> "E102: nome já declarado neste scope";
  expr.type == datatype.type
      -> "E301: o valor não tem o tipo declarado";
  not expr.secret
      -> "E602: um segredo não pode ser guardado…";
}
Mostrar a correspondência direta entre a especificação no papel e o LarkAG: as mesmas regras, nos mesmos atributos. Ler a P21: a declaração acrescenta o nome ao ambiente e ao scope; as condições verificam que não é repetido, que o tipo bate certo e que não se guarda um segredo numa variável normal.
3 · Ordem de avaliação

A gramática é L-atribuída: uma só travessia, da esquerda para a direita

blockenv = E · scope = ∅
→
var n: int = 0;envout = E ⊕ {n ↦ (int, var)}
→
n = n + 1;env já contém n
→
✔ E101 · ✔ E301n declarada · int = int

Porque é L-atribuída

Cada atributo herdado depende só do pai e dos irmãos à esquerda:

  • handlers.env = statedecls.envout (P10)
  • stmt.env = stmts₁.envout (P19)
  • handler.seen = handlers₁.handled (P13)
  • tipo da variável do for = elem(expr.type) (P27)

Consequências

  • uma travessia em profundidade chega para tudo;
  • o LarkAG calcula a ordem a partir das dependências e recusa ciclos;
  • a primeira condição de contexto que falha para a avaliação, como num compilador, e a linha do erro é a do nó em avaliação.
A pergunta "pode ser avaliada numa só passagem?" é provável. Resposta: sim, porque é L-atribuída. O exemplo mostra o ambiente a crescer: a primeira instrução declara n, a segunda já o vê.

3 · Destaque: análise de fluxo de informação

Os segredos são seguidos ao longo das expressões, até onde são usados

✔ Aceite

secret token: string = "xoxb-123";
# o segredo vai só para a credencial do notify
notify("Scan de " + str(s.src), token);

✘ Rejeitado

log("token=" + token);          # E601
var copia: string = token;     # E602
if (token == "abc") { … }        # E603
token = "outro";                 # E501

Atributo secret ↑

É verdadeiro se a expressão usa um segredo: "x" + token, str(token), token == "abc".

Fuga explícita

Um valor secreto não pode ir para nenhuma ação, nem ser guardado numa var (para não ser "lavado").

Fuga implícita

Também não pode controlar um if ou um for: o comportamento revelaria o segredo.

É a parte mais interessante da semântica e a que mais nos distingue. O atributo secret é sintetizado e propaga-se por concatenações, conversões e comparações. Distinguimos fuga explícita (passar o valor) e fuga implícita (usar o segredo numa condição).

4 · Qualidade da linguagem (NB07)

A Sentinela troca extensibilidade por fiabilidade, unicidade e consistência

FatorNívelPorquê
FiabilidadealtaÉ o objetivo: tipos estáticos, campos validados, fluxo de segredos, ações destrutivas assinaladas
ExpressividadealtaTipos, literais e ações de rede são primitivos: escreve-se ao nível do problema
UnicidadealtaUma só forma de cada construção: um ciclo, um condicional, uma declaração
Consistênciaaltanome: tipo em todas as declarações, ; e { } uniformes, uma só convenção de nomes
DocumentaçãomédiaSó comentários de linha; os esquemas alert documentam os dados de forma verificável
EscalabilidademédiaVários alertas e estado partilhado, mas sem módulos
Extensibilidade · ModularidadebaixaPor opção: sem ações do utilizador nem import, para manter a linguagem pequena
A troca é deliberada e adequada ao domínio: um playbook mal escrito pode bloquear tráfego legítimo, por isso deve ser simples, previsível e verificado. A baixa modularidade é a primeira candidata a extensão futura.

Pergunta provável: "porque é que a gramática de atributos tem tantas regras?". Resposta: mais de metade são cópias que passam o ambiente de pai para filho, que o LarkAG obriga a escrever. Decisões e limites

O que decidimos deixar de fora, e o que nenhuma análise estática apanha

Fora do âmbito, de propósito

  • ações e funções definidas pelo utilizador, módulos e import;
  • retry … until, else if em cadeia, * e /;
  • interpolação de strings ${…} (usa-se + e str());
  • tipos port e host (usam-se int e ip).

Motivo: manter a gramática pequena e o projeto realizável.

Só se sabe em execução

  • o alerta real (JSON do IDS) chega sem um campo declarado;
  • a firewall falha ao aplicar o block_ip;
  • count(…) devolve um valor inesperado;
  • log(x + ""): a mensagem vazia não é detetável estaticamente.

Por isso o W06 só deteta "" escrito diretamente.

E uma escolha de comportamento: a primeira condição de contexto que falha para a avaliação, como no LarkAG das aulas e num compilador.

Mostrar maturidade: sabemos o que fica de fora e porquê, e sabemos o que uma análise estática não consegue apanhar.
